# Phase 0.2 — Isolated Hyper-V lab deployment and release gates

Use Ubuntu Server 24.04 LTS on a dedicated Hyper-V VM, initial 4 vCPU / 8 GB RAM / 100 GB disk. Resource sizing is a target, not a measured benchmark. **Fresh installation only**: Phase 0.2 changes the bootstrap identity. Do not overwrite Phase 0/0.1 files, database, checkpoint, secrets or audit exports. Back up and preserve old evidence independently. Use a new deployment directory, data directory and dedicated Object Lock bucket. No live customer deployment is approved.

1. Inspect the source archive and install to a root-controlled project tree. Never execute root scripts from an untrusted or group/world-writable location. Review host/harden.sh before execution: it changes OS packages, SSH, firewall, auditd and Docker. Take a Hyper-V snapshot and have console access. Create root-owned host/host.conf (mode 0600) from the example. Restrict management ranges. Run the script only on a dedicated VM after reviewing generated configuration. Reconfirm SSH and firewall from permitted and denied networks.
2. Copy deploy/.env.example to deploy/.env. Use literal KEY=value entries, no shell quoting or expansion. Set SIEM_HOSTNAME to a DNS hostname, SIEM_BIND_IP to a specific management IPv4 interface address, tenant and app UUIDs, verified initial admin object UUID, dedicated DATA_DIR and nonoverlapping Docker subnets. Use a single-tenant Entra app with assignment required and phishing-resistant Conditional Access. Verify roles and sign-in policies.
3. Run `sudo bash setup.sh` in deploy. Fill secret files (not .env), restrict access, preserve keys and plan TLS certificate renewal. Trust the private CA only on approved test systems or use a valid organization-issued cert. Never disable TLS verification.
4. For immutable audit export, provision a **new dedicated versioned Object Lock bucket** with no delete permission for the exporter. Set S3 endpoint, region, bucket, retention and keys. The worker must be able to list versions and read exact versions with retention metadata. Minimum expected permissions: `s3:ListBucketVersions` on the bucket; `s3:PutObject`, `s3:PutObjectRetention`, `s3:GetObjectVersion`, `s3:GetObjectRetention` on `audit/*`. Confirm actual Wasabi requirements with a live test. Do not grant delete, bypass governance retention, bucket administration, or broad S3 privileges. Example in `deploy/s3-policy.example.json`. Configure a separate dead-man's-switch monitor that alerts if cycles fail. S3-disabled mode is for lab only; enabling export after advancing a local-only checkpoint requires an explicit evidence-preserving backfill/recovery procedure (not implemented).
5. Run `sudo docker compose config --quiet`, validate Caddy configuration, then `sudo docker compose up -d --build`. Check `sudo docker compose ps` and logs. Do not enable the `future` ClickHouse profile; no log collection exists. Verify app and worker, migration exit 0 and PostgreSQL TLS. If setup fails, investigate, do not remove security controls.
6. Verify first login with the specified immutable Entra object ID. Test wrong tenant, unassigned user, invalid token and missing CA/MFA. The browser must send the exact HTTPS Origin on POST; API clients or smoke tests must supply it. Emergency code: `sudo docker compose run --rm emergency breakglass admin@example.com`. Do not log/share codes. Test expiry, single use, demotion, concurrent consumption, rotation and logout.
7. From deploy, on a disposable database with default role names: `sudo docker compose exec -T postgres psql -U siem_bootstrap -d siem < ../app/tests/db_acceptance.sql`. This local-only bootstrap identity is used for the acceptance script because it switches roles. The migration account must not be superuser. Attempt access with each real role, confirm invalid TLS/hostname and remote bootstrap access fail, and verify denied cross-role reads/writes. Check actual data constraints, session races and administrative audit rollback.
8. Verify database-local chain via `sudo docker compose exec app python -m siem.cli verify-audit`. Independently inspect worker status and exact Wasabi versions, test deletion denial on disposable objects, confirm readback and COMPLIANCE retention. Test local checkpoint rollback and export failures in a disposable environment; verify heartbeat withheld. Never modify real evidence for a test. A mismatched local/remote checkpoint is a security alert requiring manual investigation, not a reason to reset the checkpoint. Back up and restore the database, protected keys and evidence in an isolated VM.
9. Run full pinned-dependency tests, security scanners, image scans, and capture digests. Pin all images to independently verified scanned digests before production. Confirm software supply-chain risk, including CI tool versions and OS patch level. Review residual web service trust risk in SECURITY_ASSESSMENT.md.
10. Test only authorized lab IPs: permitted/denied ingress from management and non-management networks, direct container exposure, reverse proxy errors, HTTP request boundaries, OWASP ZAP authenticated tests, load and disk consumption, backup restoration. Have an independent reviewer approve results before any customer use.
