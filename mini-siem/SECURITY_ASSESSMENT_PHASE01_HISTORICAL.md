## Threat model and residual risk

- DB head is protected against ordinary app/worker writes, not a PostgreSQL superuser or host root. The worker's independently stored authenticated checkpoint detects DB rollback through the last observed checkpoint, provided its state/key remain intact. It cannot guarantee detection of tampering before the first checkpoint or after the last anchored record. Replaying an older valid local checkpoint is possible for an attacker who can overwrite worker state. The HMAC key is symmetric; this is authentication, not a public-key signature or nonrepudiation.
- Wasabi Object Lock is intended to preserve off-host evidence; an independent operator must review latest retained **versions**, authenticate checkpoints using a separately secured copy of the key, and reconcile the chain. Automatic retrieval/comparison with the latest external anchor is not implemented. Do not claim complete malicious-root or worker-compromise protection. An attacker with the app DB credential can still manage users/sessions and fabricate new audit events; app trust remains a major residual risk. No multi-tenant isolation has been implemented.
- App is deliberately single-process. A full rate-limit table denies new keys until expiration. Attackers can degrade availability; use a managed upstream rate limiter and validate trusted proxy boundaries before customer use.
- Database certificate is valid for 365 days. Rotate it before expiry; protect CA private key offline. Local Unix socket trust is scoped to the PostgreSQL container; compromise of that container is outside the DB role isolation guarantee.
- Database owner is privileged and migration is one-shot. Docker/host root is trusted. Container escape, host hardening, network firewall policy, dependency vulnerabilities and all image versions require verification. Existing image tags are mutable. The original hashed lockfile was retained, not verified or updated.
- Worker verifies the full chain each cycle (streaming cursor), potentially expensive for large audit histories. No CPU/RAM/throughput benchmark was performed. No endpoint, syslog or detection functionality added; Wazuh remains much more capable today.
- S3 export must be configured from first deployment for complete external coverage. Switching a local-only installation to S3 requires explicit historical backfill and verification. Configure a separate bucket/prefix for this fresh deployment, not the original Phase 0 evidence.
